## Problem Statement
Startups shipping agents that read untrusted text (email, CRM notes, docs, tickets, MCP tool results) can be steered into actions: data sent out, records deleted, messages sent. RedLoop measures this from the action log, not the reply. The company problem is different from the product problem. RedLoop has strong code (13 scenarios, 65-case frozen suite, rule + LLM judge, CI gate with exit codes 0/1/3, 236 tests) and zero demand evidence. It also cannot yet run against a customer's real agent.

## Demand Evidence
- Paying customers: 0. Conversations: 0. Replies: 0. Outreach drafts: 5, unsent (startup/OUTREACH_BATCH1.md).
- Market signals, which are not demand: OpenAI agreed to acquire Promptfoo on Mar 9 2026 (openai.com/index/openai-to-acquire-promptfoo), and public agent-injection incidents exist.
- RedLoop's own live data weakens the urgency story. Meta Muse Spark 1.3 scored 0% ASR with no defenses on the frozen suite. That suite was mined against the founder's mock naive agent (STARTUP_TRACK.md). RedLoop has never produced a finding on an agent the founder did not write.
- Verdict: Q1 FAIL (unchanged from the Oct 26 hackathon pass).

## Status Quo

- Cost of the workaround: about 30 minutes, until a buyer's security team rejects the paragraph. The pain is event-driven. It exists at the moment a deal stalls on AI security evidence.
- Verdict: Q2 PARTIAL.

## Target User & Narrowest Wedge

## Recommended Approach
Approach B, with A's cheap parts run in parallel.
1. **Integration mechanism: a RedLoop MCP target that mirrors the target's own tools.** This is a small Python MCP server driven by a per-target config file. The config lists the target agent's real tool names and JSON schemas for one workflow, marks which tool is the untrusted read, and marks which tools are consequential writes.
   - The mirrored read tool returns realistic content with the injected payload inside.
   - Every mirrored write (send, delete, share, external HTTP) is a recording stub that never executes. No real mail is sent from any account.
   - The target agent keeps its own orchestration, system prompt, default model and tool names. Only the tool backends are swapped. That is the Codex shape ("keep their orchestration, prompt and tool schemas") and it addresses premise 2.
   - Stated limitation, in every report and every claim: the tools' real backends (e.g. a live inbox or CRM API) are replaced by stubs. The test measures whether the agent decides to take the forbidden action, not whether the downstream API would carry it out.
   - Task prompt: the workflow's normal user request, taken from the target's own docs or examples (e.g. "triage my new messages and follow up"). Never an instruction to read a specific poisoned item.
   - The approach is language-agnostic, so a Go agent like WUPHF needs no fork. Mapping effort per target, including paying customers: an estimated 2–4 hours to write the config for one workflow, unmeasured until the first run.
   - It reuses redloop/judge/rule_judge.py (forbidden-action rules re-keyed to the mirrored tool names), redloop/regressions.py and the check-suite exit codes 0/1/3. No mutation search, no dashboard, no LLM judge.
   - Model: the target's own default model config, so results reflect what its users run. (This is a decision, not an open question.)
2. **Target and timebox (one rule, used everywhere).**
   - Fri Oct 30, 2-hour check (verify the LICENSE file in github.com/nex-crm/wuphf first). Answer three questions:
     (a) Can WUPHF's agents load an external MCP server in place of an existing tool or integration?
     (b) Which WUPHF workflow reads untrusted text and can then act? Write down the exact tool names and schemas the MCP target must mirror.
     (c) What normal user task triggers that workflow?
     If any answer is no or unknown after 2 hours, switch to the fallback that same day.
   - Mon Nov 2 end of day: the target is wired up and the run is done. If the check passed but the run isn't done by then, take at most 2 more days (Wed Nov 4). After that, stop and switch to Letta. Pitch emails with prices stay held either way.
   - Fallback: Letta (open source, stateful agents with MCP tool support; verify). Workflow to test: a Letta agent reads a poisoned email through the RedLoop MCP tool and is checked for a `send_email` call. That test also covers poisoned-memory persistence across turns.
   - Stagehand is dropped as a fallback. It is a browser SDK and has no email-to-action path.
   - Run locally with the founder's own test setup only. Never touch a hosted instance.
3. **Case set (the exact number goes in any claim):** the 5 frozen `email_exfil` payloads, re-pointed at the mirrored tool names, plus 10 hand-written payloads that name the target's real tools and match its prompt style (per Codex). 15 cases in total. Raising the odds of a real finding matters more than reusing the mock-mined suite.
4. **Disclosure and publication rule.** Results on any third-party target go to a private directory outside the repo (e.g. ~/redloop-private/), not to results/ (which is already gitignored, but kept clean anyway). Red results, target-specific payloads and target-specific config are never committed or published until the maintainer fixes the issue or gives written permission. Only the generic MCP target code may go into the public repo. Disclosure goes through the project's SECURITY.md or security contact if one exists, and to contact@nex.ai only if none does.
5. **Use the result either way.**
   - Red: send a private disclosure with repro steps.
   - Green: send "we ran 15 injection cases through [workflow] using WUPHF's own orchestration, prompt and default model, with [tool] backends replaced by recording stubs; none landed; here's exactly what we tested and what we didn't." Offer the CI gate as an option. The judge is rule-based, but the gate still runs the agent's own model, so it needs the maintainer's model key and costs a little per run. Don't open an unsolicited PR.
   - Green-path hypothesis: a specific, honest test of their own product earns a reply where a pitch does not. Success test: a reply within 7 days. If the green email gets no reply, conclude that passing results don't create demand on their own and the questionnaire trigger (premise 5) has to carry the sale. The same 15-case run then becomes sample material for discovery calls.
6. **Discovery outreach is NOT gated on the run.** Pitch emails (with prices) wait for the result row. Question-led discovery notes ("Has a customer's security review asked you about prompt injection in the last 90 days? What did you answer?", with no price) go out Mon Nov 2 to the 4 verified non-Nex routes in startup/CONTACTS_FOUND.md:
   - Payer discovery (counts toward the conversation criteria): item via X DM @newitemco, and the Lindy contact-sales form. Both are startups whose own agents take actions.
   - Partner/content notes (do NOT count toward the conversation criteria): AgentMail founders@agentmail.cc and the Arcade contact-sales form. Both are platforms whose risk sits in their customers' agents. Same question, framed as "what do your customers ask you?"
   - Wed Nov 4 batch: up to 5 NEW names. Each must match the payer profile (a startup whose own agent reads untrusted input and takes actions) and have a founder or sales route printed on a public page (YC company page, company /contact or /security). Support@ inboxes don't count.
   - Composio, Browserbase, Smithery and Letta from startup/FIRST_10_CUSTOMERS.md are excluded. They have no usable route or are platforms, not first payers.
   - Honest count: 2 confirmed payer messages plus 0–5 still to find, so 2–7 payer messages in total. Three conversations by Nov 13 is a stretch. If fewer than 7 payer messages go out by Nov 4, the Nov 13 target moves to Nov 20.
   - The current test target's maintainer (Nex, or Letta if we fall back) hears from us only with the result.
7. **In parallel (30 min each):** publish Gumroad, add the Gumroad and site links to the README.
8. **Build freeze and delivery scope.**
   - No speculative build work after Mon Nov 2 (the MCP target plus one target run). Exception: paid delivery work for a signed customer.
   - Snapshot ($2K) scope: one agent that can load an MCP server or run through an OpenAI-compatible tool loop. Arthi writes the mirror config for the customer's real tool names and schemas for one untrusted-read-to-action workflow (estimate 2–4 hours, inside the $2K). The customer points their staging agent at the RedLoop MCP target. 15–30 cases. The report states the stubbed-backend limitation.
   - Agents that can do neither are quoted as a Full Assessment ($5K, which includes custom integration) or declined.
